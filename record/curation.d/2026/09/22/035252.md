**This came from a question, not from the lint.** Asked whether the workflow
had accumulated a ritual worth streamlining, I ran `luria --help` before
answering — and found `luria repair`, which I had not used once in four filing
units that day. Its help says it writes "every mechanical source repair",
including populating a journal entry's `created:` from its path. That is
precisely the violation I had hand-fixed in `031952.md` a few hours earlier.

**The documented sequence is four commands and the CLI has five.** `CLAUDE.md`
is explicit that it is a map and that `luria --help` wins any disagreement. The
rule is correct and it protected nothing, because the failure was not a
disagreement — it was an omission, and you do not check the help for a command
you do not know exists. A map that leaves out a road is wrong in a way its own
disclaimer cannot catch.

**Worth noticing what `repair`'s docstring says about itself:** "Prints what
changed; a second run changes nothing." It was written to be run
unconditionally, every time, and the sequence that omitted it instead
documented its weaker half.

**The hook is the smaller half of this and the more honest one.** `ADR-018` —
views land on `main` only — was held by a sentence saying to run
`git checkout -- docs/` before committing. It held four times out of four,
which reads as a good record until you set it beside the three neighbouring
disciplines that failed the same day: a stale acknowledgement directive that
shipped in `#263`, a citation to another contribution's temporary code that
shipped in the same PR, and a directive in `#269` naming `THEORY-tmp069e7`, a
code that does not exist. Every one of those was also governed by a sentence
somebody was supposed to remember. Four-for-four on the fourth discipline is
not evidence that it is reliable; it is a sample.

**What made the hook easy is that the rule is about the branch, not the
content.** `main` must be able to commit views, because CI commits them there.
A content-based check would have to duplicate `luria index`'s knowledge of its
own outputs, and would then have to distinguish a generated page from a
`README.stub`, which is a source that lives in the same tree. Checking the
branch needs none of that and is two lines. The hook is overridable with
`--no-verify` and says so, because a stub edit is legitimate and the hook
cannot tell.

**I tested it rather than reasoning about it.** Staged a file under `docs/`
on this branch, committed, watched it refuse, and confirmed `HEAD` had not
moved. That step is here because the failure mode of a pre-commit hook is
silent non-installation, and "I wrote a hook" is not the same claim as "the
hook refuses the commit".

**Three things from the same session I could not fix here, and named rather
than left implied.** The lint baseline is the big one: all day I compared
output against "7 warnings, 184 targets, 0 unbound relations, 1 unbound line"
carried in my head, which means `EXIT=0` conveys nothing and the whole output
has to be read and diffed by eye every time. An `ack` command writing
directives from `reference-status.md` would make the `THEORY-tmp069e7` class of
error impossible rather than merely caught. And a branch-side temp-code check
would have caught `#263` before it merged. All three are `luria`, not this
record, and the decision says so instead of pretending this contribution
closed them.
