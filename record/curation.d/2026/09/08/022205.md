**I merged four pull requests in under a minute and every resulting run on
the trunk failed.** Nothing about the changes was wrong. The failure was
entirely in the cadence, and it is worth writing down because the same
mistake is available to anybody with merge rights and a queue of green
branches.

## What actually happened

Each merge starts a push run. Each push run regenerates the views and pushes
them to the branch it ran on. Four of those started within seconds of each
other, so three of them finished a regeneration only to find the branch had
moved — and the recovery, pulling and rebasing their own regeneration commit
onto the winner's, conflicts by construction, because both commits rewrite
the same generated files.

The log is unambiguous, and the ordering in it is the painful part:

    rename record/principles.d/{[DP-tmpqq8o7](../design-principles.md#dp-tmpqq8o7).md => DP-008.md} (94%)
    ...
    CONFLICT (content): Merge conflict in docs/curation/2026-09.md
    error: could not apply 213771b... docs: regenerate views [skip ci]

The run **had already done the concretization correctly**. It numbered five
principles, then lost all of it to a rebase conflict on generated pages it
had also just rewritten. `main` was left carrying temporary codes, which is
precisely the state the trunk guard exists to forbid, reached by the
machinery meant to prevent it.

## Why it was not caught by the fix that preceded it

An hour earlier the views moved to the trunk only, on the argument that a
shared generated file cannot be edited by two branches at once. That
argument was right and incomplete: it removed the conflict between two
*branches* and left the conflict between two *runs on the same branch*
untouched. Serialization by placement is not serialization in time.

That is worth stating generally. **Making a file single-writer by location
does nothing about concurrent writers at that location.** The second half of
the problem is invisible while merges are spaced apart by human reading
speed, and arrives the first time they are not.

## The fix, and the smaller lesson about cadence

`concurrency:` keyed on the workflow and ref, with `cancel-in-progress:
false`, so runs for one branch queue rather than race. A burst of merges
collapses to the run in flight plus one more, and the last one regenerates
from the final source state — which is the only state that has to be right.

[ADR-002](../../record/decisions.d/ADR-002.md) had already made this argument once, for the changelog collector:
a per-merge bot commit races in-flight rebases, so collection runs on a
cadence and never per merge. The reasoning transferred to a different job in
the same workflow and nobody carried it across, which is the ordinary way a
decision fails to generalize — it was filed against the job it was about.

The behavioural half is simpler and I should have known it: **merging a stack
is not a batch operation.** Each merge is a deployment. Spacing four of them
by twenty seconds would have cost nothing and prevented all of this.
