**Two committing workflows, and the lint that stopped covering anything
([ADR-007](../../record/decisions.d/ADR-007.md)).** The record's `Docs` workflow regenerates views and commits them,
then hands its lint job the SHA it produced — that handoff exists because a
lint running anywhere else would judge the pre-regeneration commit. It works,
and it only works if nothing else commits afterwards.

`Build README` did. The observable symptom was a pull request showing green
checks whose most recent commit had never been checked, plus a `Docs` run
parked at `action_required` with zero jobs, because the bot's push had opened
a run that GitHub gates when the triggering actor is a bot.

The thing worth keeping: luria's generate action had already solved its half
by putting GitHub's skip marker in its default commit message, so its own
pushes open no runs. Every *other* committing job in this repository — the
README builder, the SVG converter, the registry builder — carried no marker.
The convention was present and unevenly applied, which is the failure mode
that looks most like working.

**What I got wrong.** I wrote the commit message for that fix with the skip
marker spelled out literally, in a sentence explaining what the marker does.
GitHub read the explanation as an instruction and skipped every workflow on
the commit. `docs.yml`'s own header comment warns about exactly this and says
to name the marker in prose; I had read that comment, edited the file
directly above it, and then did the thing it warns about.

It is worth being precise about why it took a while to notice: the failure is
not a red build, it is *no* build. The pull request went on displaying the
previous commit's green checks, which are the most recent checks that exist.
Silence is indistinguishable from success unless you are checking which
commit the green belongs to — and the first wait loop I wrote had the mirror
of the same bug, exiting immediately on "no runs in progress" when the truth
was "no runs at all". Amending the message to describe the marker instead of
spelling it produced three runs within seconds, which is the confirmation.

**Retiring the registry pipeline ([ADR-008](../../record/decisions.d/ADR-008.md)).** [ADR-006](../../record/decisions.d/ADR-006.md) had proposed inverting
the registry build so the frontend could keep consuming a generated
`registry.yaml`, and left itself `Proposed` pending a look at the frontend
contract. Looking at it made the question dissolve: the chain existed to turn
structured data into something browsable, and `docs/practices` plus
`luria site` already are that. Inverting the projection would have kept three
artifacts alive to feed a fourth that duplicates a generated view.

So the decision that superseded it deletes rather than inverts, and [ADR-006](../../record/decisions.d/ADR-006.md)
is the record's first `Superseded` decision — which is a small vindication of
the rule in [DP-003](../design-principles.md#dp-3), since the reasoning that was wrong is still readable next
to the reasoning that replaced it.

`data/` stays frozen rather than deleted. Nothing reads it at build time, but
`to_record.py` needs it, and that script is the only thing that makes 238
generated documents auditable without reading all 238.

## Not done

Settings → Pages → Source has to be switched to "GitHub Actions" by hand
before the site publishes; no file in the repository can set it. Until then
the `Pages` build job succeeds and the deploy job fails with "Pages is not
enabled". On pull requests deploy is skipped by design, so this has not been
exercised yet — the first push to the default branch is where it either
works or says that.
