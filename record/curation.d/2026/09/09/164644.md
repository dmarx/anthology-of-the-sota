Correcting a document in this record means two edits: increment `version:`,
and append an entry to `history:`. I did that by hand about thirty times
working [#114](https://github.com/dmarx/anthology-of-the-sota/issues/114), and three of them were wrong in exactly the same way.

## The failure

The natural edit is to find the `version:` line and replace it with the new
version *plus* a fresh `history:` block. That reads correctly and is wrong
whenever the document already has a history, because the new block lands
**above** the old one. Two outcomes, both caught by `luria lint`:

- a second `history:` key, and YAML keeps the last one — so the new entry
  silently disappears;
- or, where the insert merged, entries in descending order, which trips
  ``history: ends at version N but the document says N+1``.

It happened on `SOTA-034`/`110`/`111`/`112` (as one batch), on `SOTA-086`,
and again on `SOTA-111`/`112`. The first time CI caught it, because I had
been reading `luria lint` through `head -8` and its hard violations print
last. The second and third times I caught it locally, which is better and is
not the same as fixing it.

## The fix is not "be careful"

luria's own working agreement says a guard that keeps catching you is a bug
report about the workflow — one catch is the net working, the same catch
twice means the hazard is upstream. Three times is not a discipline problem.

`src/scripts/audit/bump_version.py`:

    python -m src.scripts.audit.bump_version record/practices.d/[SOTA-042](../../record/practices.d/SOTA-042.md).md \
        --note "What changed and why."

It finds the existing `history:` block and **appends** to it, starts one under
`version:` when there is none, and refuses rather than guessing if it finds
more than one `history:` key. Fired once on both paths before being trusted —
a document with four history entries (appended as the fifth, order preserved)
and one with none (block created, single key).

## The part worth generalising

The bug was invisible in the diff. Adding a correctly-formatted YAML block in
the wrong *place* looks exactly like adding it in the right place unless you
read the surrounding lines, and I was writing these edits with `str.replace`
on a version line whose neighbours I could not see.

Any edit that inserts structure near other structure of the same shape wants
a tool that knows about the structure. That is the whole lesson, and the
`_history_span` regex in the script is the only interesting line in it.
