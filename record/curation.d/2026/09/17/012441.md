## Test-time training names two different things

The box said "test-time training". Two papers answer to that name and they
are not related:

- `ARXIV-2411.07279` — temporarily update the model's parameters at inference
  using a loss built from the test instance's own examples, then discard the
  update. An **adaptation method**.
- `ARXIV-2407.04620` — a sequence layer whose hidden state is itself a model,
  updated by self-supervised learning as tokens arrive. An **architecture**,
  belonging beside [SOTA-132](../../../../practices.d/SOTA-132.md) and [SOTA-167](../../../../practices.d/SOTA-167.md) in the linear-attention line.

Filing the second under a box labelled "test-time training" would have put it
in the wrong lineage, where the record's own chain machinery would then bind
it to the wrong neighbours. So the first is filed and both documents say
explicitly that the other exists and is a different claim. A name collision
that nobody records is one the next reader re-discovers.

## The interesting result is the unglamorous benchmark

ARC is where the headline lives — 6x fine-tuned baselines, 53.0% at 8B, 61.9%
ensembled. But ARC is *built* to reward search over structurally novel tasks,
which is precisely the regime this method is defined by, so a large gain there
is close to restating the definition.

BIG-Bench Hard is the load-bearing number: +7.3 points at 10-shot on ordinary
hard reasoning. That is what says the effect is not an artifact of a benchmark
constructed to reward it. The practice weighs them that way rather than
leading with the bigger figure.

Underneath is a claim about in-context learning rather than about TTT. The
examples are identical in both conditions; used as gradient they are worth
several times what they are worth as context. So the shortfall is not missing
information in the prompt — a forward pass cannot extract what is already
there when the task is unfamiliar enough.

## Both remaining boxes were one question

Diffusion conversion and the ternary work filed earlier today are the same
decision about different artifacts: **build it that way from scratch, or adapt
something you already have.**

- Generative paradigm — [SOTA-157](../../../../practices.d/SOTA-157.md) trains as masked diffusion; the new
  practice converts an AR model for under 200B tokens.
- Quantization — [SOTA-185](../../../../practices.d/SOTA-185.md) and [SOTA-163](../../../../practices.d/SOTA-163.md) compress a finished model; the
  ternary line trains in the target format.
- Adaptation — [SOTA-123](../../../../practices.d/SOTA-123.md) pretrains a tiny model from scratch on the target
  distribution rather than fine-tuning one.

Three instances, and **no document in the record names the shape**. That is
what [DP-007](../../../../principles.d/DP-007.md) predicts of a pattern everybody uses and nobody introduced —
there is no arrival event, so nothing prompts anyone to write it down.

Deliberately left unfiled. It would be a `THEORY` rather than a practice,
because it says what is true about a family of decisions rather than what to
do in any one of them; and noticing a shape three times in one afternoon is a
reason to write the observation down, not yet evidence that it generalises.
The right move is to record it here and see whether a fourth arrives.

## A mistake caught by the lint, not by me

I cited `SOTA-tmpr318t` — the ternary practice — from these documents. It
lives on a sibling branch that has not merged, so the code resolves to nothing
here.

Temporary codes are **branch-local by design** ([LU-ADR-049](https://github.com/dmarx/luria/blob/main/record/decisions.d/ADR-049.md)): they exist so
that no branch claims a number before merges serialise. Citing one branch's
temp code from another is therefore always wrong, and it fails in two ways at
once — dangling now, and stale later when concretize turns it into a number
the prose does not carry.

The lint caught it twice over, as an unresolved code and as two broken
relative link targets (45 on main, 47 on the branch). The fix was to describe
the sibling work without citing its code. Worth recording because the error is
invisible while you are writing: both branches are in the same working tree
and the code reads perfectly well.
