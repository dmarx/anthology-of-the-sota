Nothing in the repository changed. The `github-pages` environment's
deployment branch policy was widened to admit `claude/*` alongside `main`,
and that is a repository setting — no file records it, no diff shows it, and
`git log` on `.github/workflows/` is silent about the day the meaning of
those files changed.

## What the file said, and what it meant

`deploy` was gated `if: github.event_name != 'pull_request'`. Read as prose
that is "do not publish from a pull request", which is true and is not the
rule anyone wanted. The rule anyone wanted is "publish from `main`". The two
agreed for as long as the only other way in was `workflow_run`, which carries
`branches: [main]` on the trigger.

`workflow_dispatch` was the third way in, and it takes no branch filter. It
runs on whatever ref it is dispatched from, it is not a pull request, and so
it walked past the condition. That was survivable only because the
environment refused it downstream: the job started, GitHub declined the
deployment, and the failure was loud.

Widening the policy removed the thing that was catching it. The condition did
not become wrong; it was always wrong, and had been protected by a setting
nobody was treating as load-bearing.

## The general shape

A deny-list of one entry is a claim that you have enumerated the ways in. The
allow-list version — name `main` twice, once per event — cannot be walked
past by an event nobody thought of, because an event nobody thought of is not
on the list.

It is worth naming that the two events report the branch differently. A
`workflow_run` run's own `github.ref` is not the branch of the run that
triggered it; `github.event.workflow_run.head_branch` is. A single
`github.ref == 'refs/heads/main'` covering both would have looked right and
would have gated `workflow_run` on the wrong field.

## Declining rather than revoking

The narrow fix is to revoke the branch policy. It was not taken, and the
reason is that it leaves no record: settings are not in the repository, so
the next person to want a branch preview finds neither the permission nor an
account of why it went away.

Declining in the workflow is a diff. Somebody reading `pages.yml` finds the
gate and the comment beside it; somebody reading `ADR-051` finds why a
granted permission sits unused. A permission held open and *known* to be held
open is a different object from one held open by inattention.

## What this cost

The `pull_request` trigger went with it, and that trigger was doing real work
— pages.yml's own comment described it as the proof that the site still
builds. `docs-check` covers pull-request correctness against sources, so the
record is as protected as it was. The site build is not: it now surfaces
post-merge unless someone remembers to dispatch it.

`build` is left ungated so that dispatch exists at all. That is the trade,
and it is a downgrade from automatic to remembered, which is the kind of
check that decays. One line restores it, and `deploy` is now safe enough that
restoring it is uninteresting.
