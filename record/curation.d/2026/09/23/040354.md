`#289` produced a two-item worklist from 91 candidates. Filing it is where
the sweep's output stops being a list and starts being claims.

## The network story, corrected

I reported on `#299` that the network could not reach arXiv, citing `luria
lint`'s *"140 identifiers nothing has verified — upstream could not be
reached"*. That was the right caution from the wrong evidence.

A direct request to the arXiv API returns **200** and both identifiers
verify: `2306.00978` is *AWQ: Activation-aware Weight Quantization for LLM
Compression and Acceleration*, `2208.07339` is *LLM.int8(): 8-bit Matrix
Multiplication for Transformers at Scale*. `luria remotes --resolve` returns
**HTTP 406** on every identifier it tries.

So it is not the network. It is that luria's remote cannot get through where
a plain request can — and the lint's message, which says "upstream could not
be reached", reads as the former when it means the latter. Worth knowing
before the next session declines to file something for the same reason.

## One row was two techniques wearing one name

The sweep flagged `bitsandbytes` because both `vllm` and `transformers`
carry it. That is a library, not a technique, and the obvious move is to
discard the row.

Reading it apart instead: `bitsandbytes` ships **NF4**, which the record has
held as `SOTA-230` since the QLoRA unit, and **`LLM.int8()`**, which it had
not. The row was a false positive and a true one simultaneously, and
discarding it as "that's a library" would have lost the real gap.

The general shape is worth keeping: when an adoption index names a *package*
rather than a technique, the question is not whether to discard it but how
many techniques it is.

## What the papers say that the sweep could not

The sweep can find a name. It cannot tell you what the claim is, and in both
cases the claim is narrower than the name suggests.

**AWQ's argument is about generalization, not accuracy.** Both it and GPTQ
are one-shot post-training methods at similar bit widths, and a reader
comparing headline perplexities is reading the wrong number. AWQ fits nothing
to its calibration set — no backward pass, no reconstruction — and its case
for itself is that this is why it survives instruction-tuned and multi-modal
models. That is a robustness claim, it is the one worth checking, and this
record holds no independent test of it. `compared_against` is declared
because the paper ran the comparison, which is `ADR-011`'s bar.

**`LLM.int8()`'s result is memory, not speed**, and the paper says so —
"175B on a single server with consumer GPUs", not throughput. The extra
16-bit path costs time. Practitioner reports that int8 inference is *slower*
than 16-bit at small batch are consistent with the method rather than
evidence against it, and a practice that did not say so would mislead.

**And "without any performance degradation" is an absence-of-evidence
claim** about one evaluation suite. It is a strong result. It is also exactly
the shape `DP-010` warns about — the most citable sentence being the least
supported — so both the note and the practice separate the part later work
built on (the emergent-outlier characterization) from the part a harder
evaluation could move.

## What the record now says about post-training quantization

Three practices where there were two: GPTQ's error compensation
(`SOTA-185`), AWQ's activation-chosen salience scaling, and `LLM.int8()`'s
outlier decomposition. The first two are `compared_against` each other
because their paper did it; the third is a different problem — int8
arithmetic rather than weight-only 4-bit — and is not a competitor to
either, which is why no comparison is declared.

That is the shape the sweep was for. It did not tell us any of this; it told
us where to look.
