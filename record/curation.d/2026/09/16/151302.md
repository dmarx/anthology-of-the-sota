A question — does concretization fire here after a merge? — turned into this.
It does: the decision written earlier today was numbered [ADR-038](../../record/decisions.d/ADR-038.md) on the
merge an hour before this. But
answering it meant checking which files the rename actually touches, and the
answer was *the record*, not `luria.yaml`.

`code.globs` was `src/**/*.py`. The config was scanned by nothing, and it
holds **87 code citations across 38 documents** — more than any other file
here, and all of them the same kind of claim: this is why the schema is shaped
this way. Sixteen were dead. Ten were the temporary code that became [ADR-035](../../record/decisions.d/ADR-035.md)
back in [#140](https://github.com/dmarx/anthology-of-the-sota/issues/140), which had been pointing at nothing for days.

The check's own justification, in luria's configuration reference, is that *"a
decision number in a code comment is the strongest form of the claim being
checked"*. By that argument `luria.yaml` should have been the first entry in
the globs. It was not in them at all, and nobody noticed because an unscanned
file produces no findings, which looks exactly like a clean one.

## Three things the check caught in the act of being added

**A directive that half-worked.** The first `inactive-ok-file:` named nine
codes across two wrapped lines. It suppressed the four on the first line and
silently ignored the five on the second — so the warning count dropped, which
is the signal an author reads as "it worked". Wrapping is the ordinary thing
to do at nine codes. Filed as [LU-#278](https://github.com/dmarx/luria/issues/278); noted in the directive itself so the
next person does not spend the same ten minutes.

**My own ADR, twice.** Writing the decision, I cited two luria ADRs without
the `LU-` prefix — the exact bug the contribution exists to fix, committed
while fixing it. Then the dead temp codes I had quoted *as examples of dead
temp codes* were read as citations, and one of them voided the annotation
meant to cover them. Backticks do not make a code a mention here, whatever I
remembered.

**A stale directive is itself a finding.** Naming one unknown code in an
`inactive-ok-file:` voids the whole annotation — and luria says so, naming
what was left unacknowledged as a result. That is the behaviour to want: the
failure was loud instead of quiet, which is the entire difference between this
and the sixteen citations that rotted in silence.

## The general shape

Every finding in this contribution has the same structure. Something was
true, then stopped being true, and the mechanism that would have said so did
not cover the place it happened. Concretization rewrites the record;
`luria link --fix` rewrites record prose; neither touches a code-glob file,
and the config was in no category at all.

Left open, and it has no mechanism anywhere: a *remote's* temporary code.
[LU-ADR-084](https://github.com/dmarx/luria/blob/main/record/decisions.d/ADR-084.md) was cited here as a temp code from luria's repo. No local merge can
fix that, because the concretization that resolved it happened in a different
repository. The lint now reports it as unresolved, which is how this one
surfaced — but reporting is all there is.
