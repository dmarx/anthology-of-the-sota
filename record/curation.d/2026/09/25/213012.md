Three times in one session a rebase onto `main` conflicted on record files that
had been renamed underneath the branch. Each time I aborted, reset, and
re-applied the amendments by hand. In reporting the third I wrote that "CI
concretized the temp codes mid-work", which reads as a misconfiguration
and is not what happened.

## What actually happens, which is the design working

`docs.yml` guards the generating job with `if: github.event_name == 'push'`, and
the only push branch is `main`. `concretize: "true"` appears once, in that job,
with a comment saying why:

> Assign real numbers to merge-allocated temporary codes ([LU-ADR-049](https://github.com/dmarx/luria/blob/main/record/decisions.d/ADR-049.md)) — only
> where merges serialize, which is this job. Concretizing on a branch is the
> premature number claim the temporary codes exist to avoid.

On `#367` the PR's own checks were `docs-generate` **skipped**, `docs-lint`
skipped, `collect` skipped, `docs-check` success. Nothing concretized on the
branch. The renames landed in `d7dfdcf3`, a bot commit on `main`.

**So the temporary codes were on `main` because they have to be.** They are the
mechanism by which a branch declines to claim a number; the PR merges carrying
them and the trunk assigns numbers afterwards. That leaves a window in which
`main`'s tip is legitimately inconsistent:

| commit | time (UTC) | state |
| --- | --- | --- |
| `0e9a81e0` | 18:40:55 | merge; tip carries three temp codes |
| `d7dfdcf3` | 18:41:57 | bot renames them to `LIT-693`, `SOTA-424`, `THEORY-109` |

Sixty-two seconds. I branched inside it.

## The part that was mine, and it is the reusable bit

Branching into a 62-second window is bad luck. Failing to notice afterwards was
not. When the fetch showed `d7dfdcf3` had arrived, I tested for concretization
with

    ls record/literature.d/[LIT-693](../../record/literature.d/LIT-693.md).md

which reads the **working tree** — descended from the merge commit, so of course
the temp file was there. I concluded "no concretization", carried on, and let
the rebase discover it.

**A local path check cannot answer a question about a remote ref, and it fails
reassuringly rather than loudly.** The right check names the ref:

    git ls-tree -r --name-only origin/main record/ | grep -c tmp

That is the generalisable shape: when the question is "what does the trunk look
like now", every answer that reads the checkout is measuring the wrong tree, and
a descendant of the thing you are asking about will always agree with you.

## Why the grep is a stopgap and not the fix

`luria concretize --check` exists and is described as "the trunk's guard" — but
it reads the working tree, because on `main` that is the right place to look. The
brancher's question is the inverse and is about a ref, so the same command
cannot serve it as written. Filed as `LU-#325`.

The argument for the CLI owning it rather than this file carrying a grep is that
every way the grep is wrong is something the CLI already knows: `grep tmp`
matches any path containing the substring, ignores which schemes are
merge-allocated, hardcodes `record/` as the layout, and would go silently stale
if a project ever configured a different sentinel. `config.TEMP_TAIL`,
`current().schemes` and `cfg.rel()` are the configured answers to all four.
`CLAUDE.md` says to delete the grep when that ships, because a workaround with
no expiry date outlives the thing it works around.

## Not the same as [LU-#309](https://github.com/dmarx/luria/issues/309)

That issue is a branch *citing* a temporary code it did not mint — another open
branch's, which the reference scan reports as "temporary codes this record does
not mint". This is a branch *inheriting* temp codes from the trunk that are about
to be renamed underneath it. Same mechanism, opposite direction, and no report
covers it because at branch time there is nothing yet to scan.
