Unit 4 of `#342`. The unit is worth writing up for the thing it **did not**
find, because the ranking predicted a defect and the prediction was wrong in a
way that was cheap to establish and would have been expensive to get wrong.

## The prediction

`#342` ranked `2112.05682` fourth with this row:

> 61 files, 5 practices name FlashAttention. `SOTA-085` (`Active`) carries
> `introduced_by: LIT-074` — Dao et al., **May 2022**. Same shape as `#338`;
> verify before asserting.

The arithmetic is right: Rabe and Staats is December 2021, FlashAttention is
May 2022, and `SOTA-085` credits the later one. After two units where exactly
that pattern was a real defect, the pull toward a third repair was strong.

## Why it is not the same shape

`SOTA-192`'s title was **normalize the queries and keys before the attention
dot product** — a generic technique, credited to a paper that had adopted it
and whose own note declined the credit.

`SOTA-085`'s title is **use flash attention**. That names an artifact. Flash
attention is Dao et al.'s system: the CUDA kernel, the IO-aware framing, the
HBM-access bound, the derived block sizes. The recommendation to run *that
thing* was first made by the people who built it, and no amount of antecedent
changes it.

The distinction generalises and is worth having: **a practice whose title
names a technique can be credited to the wrong paper; a practice whose title
names an artifact usually cannot.** The failure mode for the second kind is
different — it is that the artifact's paper gets credited with the ideas
underneath it, which is what `LIT-074` was doing by naming no antecedent at
all.

So `introduced_by` is unchanged, and the argument is written into the
practice's Source section rather than only here, so the next pass over this
line does not re-open it.

## What was actually there

The paper carries a number the record needed and did not have, and it is in
the abstract:

> is **within a few percent of the runtime of the standard implementation** of
> attention

Same algorithm, same exactness, same 59× memory reduction at 16,384 tokens —
and no speedup, because *"standard self-attention already balances the
available FLOPs and memory bandwidth of TPUs."* They repeat the point about
chunk sizes: `√n` is optimal for memory, and the runtime consequence is
*"heavily affected by the choice of hardware."*

So `SOTA-085` had been carrying **two claims as one**. Less memory is a
property of the algorithm and holds wherever it runs. More speed is a property
of a memory hierarchy where HBM traffic is the bottleneck — which is the GPU
case `LIT-074` measures, and explicitly not the TPU case measured here.

`SOTA-085`'s existing condition section is about whether the **kernel runs**:
on-chip memory per SM, head dimension, dtype, a compiled path. That is a real
condition and it is not this one. This one is about whether the **benefit
transfers**, and nothing in the record asked it.

## The shape underneath both

`LIT-074` said it was the source of four confirmed practices and named nothing
before it. The chain is three deep:

- **Jang et al. (2019)** — the algebraic identity. Rabe and Staats call their
  own Equation 1 *"a rediscovery"* of it.
- **Rabe and Staats (2021)** — the memory-complexity result, stability,
  differentiation, a working implementation.
- **Dao et al. (2022)** — IO-awareness and a CUDA kernel that converts the
  memory saving into wall-clock time on GPUs.

Each link credits the one before it *in its own paper*. The record held the
last one and none of the credits, which is the same transitive-hedge shape
`#338` filed: **the citation travels along the edge and the attribution does
not.** Three units in a row have now turned on reading a paper's related-work
section, and the cost of that reading is minutes.

## What the unit says about ranking

`#342` got this one wrong and got it wrong **usefully**, because the row said
*"verify before asserting."* A ranked queue whose rows carry their own
uncertainty is worth more than one that only carries confidence, and the
cost of the wrong prediction here was a single fetch.

The pattern to avoid is the one that nearly happened: two consecutive units
finding the same defect makes the third look like a foregone conclusion.
**Three instances is where a shape starts generating false positives rather
than finding true ones**, and the guard is the one the issue already had —
state the prediction as a prediction, and read the paper.
