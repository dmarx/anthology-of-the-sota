**The tell was that resolving the conflicts was never interesting.** Four
times today two branches collided on generated pages, and four times the
resolution was the same ritual: `git checkout --theirs docs/`, rerun `luria
index`, re-stage, commit. Nothing was learned. No judgement was exercised.
The correct content was a pure function of sources that were not themselves
in conflict.

That is the signature of a file in the wrong place, and it took four
repetitions to read it as one rather than as friction to be absorbed. Luria's
own principle covers this — a guard that keeps catching you is a bug report
about the workflow — and the same shape applies to a merge conflict that
keeps arriving with no information in it.

## What the cost actually was

Not the resolutions. The resolutions were minutes. The cost was:

- **A recovery from a failed `git stash pop`** earlier in the day, where
  regenerated views blocked the merge and four untracked notes had to be
  verified intact by hand before anything could proceed.
- **A second conflict on the same branch after the first merge**, because the
  bot's regeneration commit on `main` rewrites the same shared files — and
  that time `luria concretize` had also renamed the temp-coded documents the
  first merge numbered, so the second resolution was against files with
  different names.
- **A stack three deep** that had to be collapsed and landed in one merge to
  avoid two more rounds of it.

None of that is inherent to the work. All of it came from regenerating
shared files on branches.

## The fix, and the thing that made it available

`docs.yml` now mirrors the shape luria uses on its own record: generate and
commit views on the push to `main`, and on a pull request run the generate
action with `views: "false"` plus the lint action in the same job, so source
repairs land on the branch and no view is written.

Worth recording how close this came to being blocked. Checking whether the
pinned action supported `views:` at all, the first attempt was `git show
0.11.0:actions/generate/action.yml` in a clone whose tags had never been
fetched — the tag did not resolve, the command failed, the `|| echo "NOT
PRESENT"` fallback fired, and the answer read as a clean negative. It was
wrong. `views:` is in 0.11.0.

**A shell fallback that cannot distinguish "absent" from "the lookup
failed" will report the second as the first**, and it will do so in the
confident voice of a successful command. The same shape as suppressing
stderr, which this journal already records once. The version that would not
have lied: resolve the ref first, then read the file, and let the failure be
a failure.

## What it changes for a contributor

Run `luria index` locally anyway — `docs/reports/reference-status.md` is what
tells you which citations the lint is about to flag, and reading it before
writing acknowledgements is the fix for the *other* recurring mistake this
week. Then throw the views away before committing. A branch carrying views is
not more up to date; it is a conflict with every other branch.
