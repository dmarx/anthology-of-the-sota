`LIT-052` was found by hand: five practices had no bodies, writing them
meant reading the paper, and the paper turned out to be about something
else entirely. That is an expensive way to find a defect, so the obvious
next question was whether the same class could be found mechanically
across all 223 notes.

Partly, yes. The check that works is **`first_author` against the arXiv
API's author list**, and it found five wrong names in 210 resolvable ids.

## What the sweep can and cannot catch

`arxiv:` ids all resolve, and every declared `title:` matches the title
at its id — 0 findings on both. That is the reassuring half and also the
trap: `LIT-052` passed both of those checks. Its title, id, author and
year were all correct and mutually consistent. Only the *content* was
another paper's, and no API call can see that.

So the sweep is worth keeping, and it does not close the `LIT-052` class.
The bullets under a note are checkable only by reading, which is what the
`#107` body backlog turned out to be doing as a side effect.

## The five

| note | declared | actual | how it went wrong |
|---|---|---|---|
| `LIT-030` | `Noam` | Shazeer | given name in a surname field |
| `LIT-086` | `Nerfstudio` | Fridovich-Keil | a software project, not a person |
| `LIT-087` | `Liu` | Xie | a name belonging to nobody on the paper |
| `LIT-107` | `Ranftl` | Birkl | right series, wrong paper's first author |
| `LIT-115` | `Bhardwaj` | Fu | a name belonging to nobody on the paper |

`LIT-107` is the instructive one. Ranftl leads the original MiDaS papers;
`arXiv:2307.14460` is MiDaS v3.1, whose first author is Birkl. A series
where the first author changes between versions defeats the check a human
does, which is "does this name sound right for this work" — it does.

`LIT-115` is the one that cost something. Its wrong name was rendered
into the prose of `SOTA-110`, `SOTA-111` and `SOTA-112`, so "Bhardwaj et
al." appeared six times across the record for a paper with no Bhardwaj
on it.

## The trap in writing the sweep

The arXiv API **does not return entries in `id_list` order**. Pairing
requests to responses positionally produced 166 "id mismatches" and,
because the id check `continue`d past the author and title checks, *zero*
author findings — a result that looks like a catastrophe and a clean bill
of health at the same time. Key results by the `<id>` in the response.

The tell was the shape, not any single row: 166 of 172 wrong is not a
corpus with a problem, it is a script with one. A defect rate near 100%
should always be read as a bug in the detector first. The same mistake in
the other direction had already happened this session, where a body
detector that accepted `## Known implementations` reported zero remaining
work while seven practices were empty.

## What CI caught that I did not

The version bumps that came with these corrections were written by a
script that inserted each new `history:` entry at the *top* of the list.
`luria lint` requires history to **end** at the document's current
version, so four practices failed with "`history:` ends at version 2 but
the document says 3".

That is the guard working. What is worth recording is why it reached CI
at all: I had been reading `luria lint` through `head -8`, and the
violations print *after* the warnings and the pending-decisions line. The
warning count looked unchanged, so the run looked clean.

`luria lint` is warn-first and its hard violations come last. Read the
tail, or read all of it — a truncated lint is not a lint.

## Also checked, no action

Three arXiv ids are each held by two notes: `2302.06675` (`LIT-090`,
`LIT-105`), `2002.04745` (`LIT-029`, `LIT-114`), `1608.03983` (`LIT-006`,
`LIT-042`). All three pairs were already triaged — one of each is
`Rejected` or `Superseded`, and only `LIT-114` is cited. Duplicate ids
are worth a periodic look but are not currently a defect.

Seven notes declare a corporate author (`Kimi Team`, `Olmo Team`,
`Falcon-LLM Team`) that the API returns with the words in the other order
(`Team Kimi`). These are false positives of the surname check, not
findings, and the sweep should special-case them rather than have someone
re-triage them next time.

## Re-running it

    python -m src.scripts.audit.verify_arxiv

The script is committed rather than described, because a sweep worth
running twice is worth not rewriting. It carries the two things that were
expensive to learn — batch the `id_list` at 40 with the API's own
three-second pause, and key results by the returned id — and it
special-cases corporate authors so the seven false positives do not come
back.

Fired once against three deliberately re-introduced defects before being
trusted: `LIT-115`'s wrong author, `LIT-107`'s wrong author, and a title
swapped onto `LIT-096`. All three caught, both check types firing. On the
corrected record it reports zero findings and the three known duplicate
ids.
