Looking for practices hidden from the graph the way GRPO was turned up
something worse than an absence.

## The record was arguing with itself

| | | |
|---|---|---|
| [SOTA-023](../../record/practices.d/SOTA-023.md) | `Active` | "Use multi-query attention for decoder-only models" |
| [SOTA-024](../../record/practices.d/SOTA-024.md) | `Active` | "Keep key/value projections shared across heads" — the same paper, the same claim |
| [SOTA-109](../../record/practices.d/SOTA-109.md) | `Active` | "Prefer GQA to MQA or MHA" |

All three in force at once. Two of them recommend the thing the third
recommends against.

None of this was visible to any check. Each document is individually valid —
a real source, a resolvable code, a status from the vocabulary — and nothing
in the record compares two practices' *claims*. The lint cannot know that
"use MQA" and "prefer GQA to MQA" are the same question answered twice.

All three were migration stubs: a title, a source line, no body. That is what
made it survivable for so long. A practice with no body has nothing to
contradict.

## And the successor was sitting in the corpus

[LIT-174](../../record/literature.d/LIT-174.md) is DeepSeek-V2, the MLA
paper. Its own standing section says filing it "closes the largest single hole
the architecture half of the record had" — and then no practice was drawn from
it. Meanwhile [SOTA-132](../../record/practices.d/SOTA-132.md) already
recommends a layer layout **defined in terms of MLA layers**, so the record
was recommending a ratio of a thing it had never defined.

MLA is filed `Active`, `emerging`. `Active` because four models across two
labs from 236B to 1.6T is unusually strong evidence for an architecture
choice. `emerging` because two labs is not the field: Llama, Qwen and Mistral
still ship GQA, and the record is out slightly ahead of consensus here, which
is the corner [ADR-015](../../record/decisions.d/ADR-015.md) added the second
axis to be able to say.

It does **not** supersede GQA. They are `compared_against`: two answers to the
KV cache that give up different things, and GQA stays the default for a model
not paying MLA's implementation cost.

## Two attributions that were simply wrong

`first_author: 'Dao'` on Shazeer's "Fast Transformer Decoding". `'Yang'` on
Ainslie's GQA. Both propagated into three practice summaries.

Checked against the arXiv API rather than corrected from memory, which is the
same standard the id repair held itself to. Worth noting what the existing
guard does and does not cover: `luria lint` compares recorded **titles**
against arXiv, so both notes passed every run. Nothing checks authors.

## What the temp code hid

[SOTA-145](../../record/practices.d/SOTA-145.md) cites [SOTA-146](../../record/practices.d/SOTA-146.md) in prose without an acknowledgement, and that
finding could not appear until after the merge that concretized the codes.

This entry first said that was because "there was no document for it to have
a status", which is wrong: the file existed throughout and carried
`status: Proposed` in its own frontmatter. The real reason is two independent
blind spots, and both have to be true for the finding to stay hidden.

**The document is not loaded.** `Scheme.documents()` keys by number and skips
any file it cannot get one from, so a temp-coded document never reaches
`load_docs()`. The status checker holds no record of it at all.

**The citation is not scanned.** `ref_status.CODE_RE` is
`[A-Za-z]{2,10}-\d{1,4}` — digits required — so the text `SOTA-tmpauaby`
does not match a citation site either.

So a merge-allocated document is invisible to the status checker from both
ends, and the asymmetry is the interesting part: the *link* checker handles
temp codes fine, which is how `luria link --fix` wrote these references in
the first place. Reference resolution and reference *standing* disagree about
whether a temporary code is a code, and only one of them says so.

Filed upstream as [dmarx/luria#203](https://github.com/dmarx/luria/issues/203).
