The query I had promised turned out to be unanswerable, and the query that
replaced it found something the record had already written down three times.

## The dead query

I proposed, in the last pull request, to build the query that separates method
papers from model reports. [ADR-032](../../record/decisions.d/ADR-032.md) names the discriminator and it is not a
frontmatter field: a paper that deliberately carries no practice **says so in
its own body**, and both exemplars open their standing section with the same
bold phrase. So the ranking is a text search, which is fine — except that of
the 109 notes supporting no practice and no theory, exactly **two** write it.
Both are the exemplars [ADR-032](../../record/decisions.d/ADR-032.md) itself cites.

A convention with two adopters out of the 109 documents it was written for is
not a signal to rank on. The honest finding is about the convention rather
than about any paper, and it is now on the record here rather than dressed up
as a result.

## The query that replaced it, and what my first shape could not see

Splitting the same 109 by how they are actually *used*:

| bucket | n | what it means |
|---|---|---|
| declared | 2 | says it carries no practice, deliberately |
| prose-cited | 15 | load-bearing in a practice's body, the source of none |
| read-only | 77 | has a reading; nothing refers to it |
| inert | 15 | not even a reading |

The `prose-cited` bucket only exists because the first version of the query
was wrong in a way it could not report. I had grouped by the `source`,
`introduced_by` and `contested_by` fields, which is correct at the field
level and blind to the level that matters: [SOTA-208](../../../../practices.d/SOTA-208.md) leans on [LIT-033](../../../../literature.d/LIT-033.md) at line
92 of its body and names it in no field at all. [DP-004](../design-principles.md#dp-4) on my own pass — the
query found only the defect it was shaped like, and the fix was to widen the
shape rather than to trust the count.

## What the inert bucket turned up

Three pairs of notes sharing one arXiv identifier: [LIT-006](../../../../literature.d/LIT-006.md)/[LIT-042](../../../../literature.d/LIT-042.md),
[LIT-029](../../../../literature.d/LIT-029.md)/[LIT-114](../../../../literature.d/LIT-114.md), [LIT-090](../../../../literature.d/LIT-090.md)/[LIT-105](../../../../literature.d/LIT-105.md). None is a defect: every one is already
retired, pointing at its survivor, with the reason written into the body.

What is worth recording is that **all three stop to name the same missing
check**, in three documents written weeks apart:

- *"two documents can name one source and the lint stays clean"* — [LIT-105](../../../../literature.d/LIT-105.md)
- *"no check in the record compares identifiers across notes"* — [LIT-029](../../../../literature.d/LIT-029.md)
- *"a paper has one standing, and two notes for it is a data error rather
  than a difference of opinion"* — [LIT-006](../../../../literature.d/LIT-006.md)

Each names [LU-#165](https://github.com/dmarx/luria/issues/165), open since 5 September. A fact the record writes down
three times, in three places, at three different moments, is one the tooling
should be asserting — and I only found the pattern because a query about
something else happened to land on all three at once.

## What was built

`unique:` in luria ([LU-ADR-111](https://github.com/dmarx/luria/blob/main/record/decisions.d/ADR-111.md), released in 0.27.0), and this record declares
it on the `source` field group. The pin and the declaration move in the same
commit deliberately: I checked, and 0.26.0 **silently ignores** the key and
lints clean, so landing the declaration first would have given this record a
constraint nothing checked — an absence reading exactly like a success, which
is the failure the check is partly there to prevent.

The design point that makes it usable: **a duplicate retired naming its
survivor is the resolution, not the finding.** Retire-by-status means a
correctly-handled duplicate is still here, still holding its identifier, so a
naive check fires on every pair this record has already answered and makes the
answer look like the defect. The check clears on the `superseded_by:` pointer
rather than on a status — and [LIT-090](../../../../literature.d/LIT-090.md)/[LIT-105](../../../../literature.d/LIT-105.md) is why, because there *both*
notes are Rejected, the survivor for its own unrelated reasons. All three
pairs pass with no directive.

## Fired before trusting, twice

The check reports zero on this corpus, which is indistinguishable from a check
that cannot run. So: remove the `superseded_by:` pointer from [LIT-105](../../../../literature.d/LIT-105.md), leave
its `Rejected` status untouched, and it names exactly [LIT-090](../../../../literature.d/LIT-090.md)/[LIT-105](../../../../literature.d/LIT-105.md);
restore the pointer and it clears.

Run twice on purpose. The first was against the development checkout, which
proves the source is right and not that the artifact is — the released wheel
is a different thing, and it is the thing CI installs. The second was against
`luria==0.27.0` from PyPI in a clean environment, and only that one licenses
the pin.

## The trap I walked into anyway

Writing the decision in luria, I cited `DP-2` and `DP-15` from memory and
**both were wrong**. luria and this anthology each keep their own design
principles under the same `DP-` prefix, and I had written this record's
numbering into that one — luria's [DP-002](../design-principles.md#dp-2) is about contribution locks, not
about a uniform field carrying no information. Caught by opening the files
rather than by any check, since both codes resolve perfectly well; they simply
resolve to other principles than the ones the sentences described.

The right ones turned out to make the argument better than the invented ones
would have. luria's DP-010 says a check defaults ON, which the opt-in design
owes an answer to, and having to write that answer produced the follow-up
worth having: uniqueness over the fields a remote already resolves, which
needs no declaration at all.

Nothing in either record's lint can catch this class, because a cross-record
citation from memory lands on a code that exists. The only defence is the one
that worked: open the document before quoting what it says.
